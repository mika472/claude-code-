# 返信案を60秒で作る デモ一式（顧客管理課向け）

スライド3枚（タイトル／AIが出す3つ／困りごと3つ）に接続する、実演用の一式です。
進行卓（`console.html`）を手元の2画面目で開き、投影画面ではAIのチャットだけを見せます。

デモの設計方針：**スライドの「困りごと3つ」を、デモの3つの場面で1つずつ潰す。**

| 場面 | 操作 | 潰す困りごと |
|---|---|---|
| 60秒で3点出力 | マスタープロンプト＋問い合わせ | 1. 担当者ごとに言い回しが違う |
| 区分を1行書き換え | `一般` → `VIP` | 2. 敬語の強さに毎回迷う |
| 指摘をルールに書き戻す | 差分修正 → ルール恒久化 | 3. 同じ指摘が何度も戻る |

---

## 1. 進行（約10分）

| 時間 | やること |
|---|---|
| 開始5分前 | 新規チャット1つだけ。サンプルAで1回空回しして出力形を確認し、チャットを消す |
| 0:00 | つかみ「この場で60秒やります」 |
| 0:30 | 困りごと3つを置く。「どれが一番近いですか」と1人に聞く |
| 1:30 | 入力を見せる（マスキング済み。まだ送信しない） |
| 2:00 | **60秒を回す**（送信と同時にタイマー開始。待つ間に「3つ作っています」と話す） |
| 3:00 | 出力を読む。【要確認：回答期日】を指す → 困りごと1 完了 |
| 4:00 | VIPに切替。「変わったのは3箇所だけ」 → 困りごと2 完了 |
| 5:00 | 上席の指摘3つを差分修正で反映 |
| 6:30 | **指摘をルールに書き戻す**（山場） → 困りごと3 完了 |
| 7:30 | 要確認リスト＝安全装置。人の承認を外さない運用を宣言 |
| 8:30 | 締め。次アクションは1つだけ（「御社の問い合わせ10件で作ります」＋日程） |

話す言葉はすべて `console.html` に入れてあります。

---

## 2. プロンプト

### ① マスタープロンプト

```
# 役割
あなたは顧客管理課の返信文作成アシスタントです。

# 顧客区分
一般

# 出力（この3つだけ。前置き・あとがきは書かない）
## 1. 件名案（3つ）
用件が1行で分かるもの。全角15〜25字。
## 2. メール本文
全角300〜400字。構成は「宛名 → お詫びまたは御礼 → 事実の受け止め → 対応内容 → 期日 → 結び」。
1文は40字以内。箇条書きは3点まで。
## 3. 要確認リスト
送る前に社内で確定が必要な事項。各行に「確認すること / 確認先」を書く。表で出す。

# 絶対ルール
1. 原文に書かれていない金額・日付・手数料・規程名・担当者名を、推測で書かない。
2. 書く必要があるが確定していない箇所は、本文中に【要確認：○○】とそのまま残す。
3. お詫びは冒頭の1回だけ。文末で繰り返さない。
4. 「たぶん」「〜と思います」など担当者の主観は書かない。
5. 社内用語・略語は使わない。

# 文体（顧客区分で切り替える）
- 一般：丁寧語＋謙譲語。二重敬語は使わない。前置きは1文まで。
- VIP：冒頭に日頃のお取引への御礼を1文足す。各段落にクッション言葉を1つ入れる。
  結びに担当者の直通連絡先の行を足す。増やすのは合計100字まで。

# 問い合わせ原文
"""
（ここに貼る）
"""
```

### ② 差分修正（上席の指摘）

```
いまの本文を、下の指摘だけ反映して直してください。
出力は次の順です。
1. 変更点の表（指摘 / 変更前 / 変更後）
2. 修正後の本文（全文）
指摘にない箇所は変えないでください。

指摘
1. 長い。280字以内にする。
2. お詫びは冒頭の1回だけにする。
3. 返金の可否はまだ決まっていないので、断定せず【要確認】のまま残す。
```

### ③ ルール恒久化（山場）

```
いま出した指摘3点を、次回から毎回守るルールとして、
最初のプロンプトの「絶対ルール」に追記する形で書き直してください。
出力は、書き直した「絶対ルール」の部分だけで構いません。
```

返ってきた文を①に貼り替えて画面で見せる。ここを飛ばすと、ただの便利ツール紹介で終わります。

### ④ 自社文体の学習（質疑で求められたら）

```
これから、実際に送った返信を5通お見せします。
この5通に共通する書き方（挨拶の型・段落の順番・よく使う言い回し・避けている表現）を
箇条書きで抜き出し、最初のプロンプトの「文体」欄に入れる形で書き直してください。
推測で足さず、5通から読み取れたものだけを書いてください。
```

## 3. サンプル問い合わせ（マスキング済み）

### サンプルA（本番用）

```
件名：先月の請求について

【社名A】の【顧客名A】と申します。
先月末に届いた請求書の金額が、前回より高くなっていました。
契約時の説明では、月額は変わらないと伺っていたと思います。
明細を見ても、何の費用が増えたのか分かりません。
至急、内訳のご説明と、もし誤りであれば返金の対応をお願いします。
あわせて、今月末に社内の決算がありますので、それまでに書面をいただきたいです。
担当の方からの折り返しも、前回お願いしたのですが届いておりません。

契約番号：【契約番号A】
電話：【電話番号A】
```

この文を選んだ理由：論点が4つ（金額差異・返金・期日・折り返し漏れ）あり、どれも原文からは確定できない。
したがって要確認リストが必ず4〜5件出て、デモの肝が自動的に立ちます。

### サンプルB（予備・場が硬いとき）

```
件名：契約内容の変更について

お世話になっております。【社名B】の【顧客名B】です。
来月から拠点が1つ増えるため、利用アカウントを5つ追加したいと考えています。
追加分の料金と、手続きに必要な書類を教えてください。
開始は来月1日を希望しています。
また、現在の契約期間の途中でも追加は可能でしょうか。

契約番号：【契約番号B】
```

### マスキング・ルール

| 元の情報 | 置き換え |
|---|---|
| 氏名 | 【顧客名A】 |
| 会社名・部署名 | 【社名A】 |
| 契約番号・口座番号 | 【契約番号A】 |
| 電話・メール・住所 | 【電話番号A】 |
| 個人が特定できる金額・日付 | 【金額】【日付】 |

参加者が自社の実文を貼りたいと言い出したら、この表を先に見せ、「伏せてからお預かりします」と宣言してから受け取る。

## 4. 保険（想定出力）

回線が落ちた・出力が崩れた時に出すもの。どう出るはずかの見本でもあります。

**件名案**

```
1. ご請求額についてのご確認とお詫び
2. 先月分ご請求の内訳確認のご連絡
3. ご請求内容の確認と今後の対応について
```

**メール本文（一般・約330字）**

```
【社名A】
【顧客名A】様

お世話になっております。顧客管理課の【要確認：担当者名】でございます。
このたびはご請求内容にご不明な点をおかけし、またご連絡が遅れ、誠に申し訳ございません。

先月分のご請求額が前回より増えているとのこと、承りました。
現在、以下を確認しております。

・ご請求額が増えた理由と、該当する明細項目
・ご契約時のご説明内容との相違の有無
・誤りであった場合の返金の可否と手続き

確認の結果は、【要確認：回答期日】までに書面でお送りいたします。
貴社の決算のご予定も承っておりますので、間に合うよう進めてまいります。

ご不便をおかけし恐縮ですが、今しばらくお待ちくださいますようお願い申し上げます。
```

**要確認リスト**

| 確認すること | 確認先 |
|---|---|
| 先月分の請求額が増えた理由と該当項目 | 経理 / 請求システム |
| 契約時の説明内容（月額据え置きの案内の有無） | 営業担当 / 契約書控え |
| 誤請求だった場合の返金可否・手数料・手続き | 経理 / 社内規程 |
| 書面での回答期日（先方の決算に間に合うか） | 上席 / 顧客に確認 |
| 前回の折り返し依頼が未対応になった経緯 | 対応履歴 / 前回担当者 |

**VIPに切り替えると変わる3箇所**

| 箇所 | 加わる文 |
|---|---|
| 冒頭 | 平素より格別のお引き立てを賜り、厚く御礼申し上げます。 |
| 各段落 | 恐れ入りますが／差し支えなければ／誠に恐縮ながら |
| 結び | 本件は私【要確認：担当者名】が直接担当いたします。直通：【要確認：直通番号】 |

## 5. 想定質疑

| 質問 | 答え方 |
|---|---|
| 間違った内容を送ってしまわないか | だから要確認リストを3つ目に出している。無編集での送信は運用ルールで禁止する |
| 個人情報を入れて大丈夫か | 全てマスキング済み。実運用は学習に使われない法人契約で。取り扱い方針は顧問の弁護士・社労士に確認を |
| 文体が自社と違う | 実際の返信5通から型を抜き出す（プロンプト④）。ゼロから作らず、今の文体を写す |
| 人が直すなら時短にならないのでは | 速くなるのは「白紙から書き始めるまで」。導入前に現状の1件あたり所要を実測すること |
| 毎回貼るのは面倒では | 実運用では定型登録し、担当者は問い合わせ文を貼るだけにする |
| 本当に60秒か | 入力長と回線で前後する。だいたい1分、長くて2分 |

---

## 6. 先に言っておくリスク

1. **AIは事実を作る。** 要確認リストと人の承認を外した瞬間に、誤情報が顧客に届く経路ができる。
2. **情報漏えい。** マスキングの徹底と、学習に使われない契約形態。法務面は専門家（弁護士等）に確認を。
3. **プロンプトの属人化。** 「ルールを1か所に集める」は、その1か所を誰が管理するか決めない限り機能しない。
4. **品質の下限は上がるが、上限は上がらない。** 一番うまい担当者の文より良くはならない。
5. **現場の反発。** 「AIに書かせるのか」への答えを課長が自分の言葉で持っていないと定着しない。

| 項目 | 置いた前提 |
|---|---|
| 1件あたり | 15分 → 5分（10分短縮） |

## デモが壊れる原因と対処

| 症状 | 原因 | 対処 |
|---|---|---|
| 出力に長い前置きが付く | 前のやり取りが残っている | 新規チャットから始める |
| 3見出しで出ない | プロンプトの一部しか貼れていない | 貼り直す。途中送信しない |
| 60秒を超える | 入力が長い／回線 | 待つ間に話す台本（ステップ4）を使う。焦らない |
| 止まった・落ちた | 回線 | 復旧を試みず、保険を出して進む |
| VIPの差が分かりにくい | 問い合わせ文を一緒に変えてしまった | 区分の1行だけを書き換える |
